# NovelRAG 一键 AI 准备方案

日期：2026-10-01。状态：用户已批准实施；执行与验证记录见 ../plans/2026-10-01-one-click-ai.md。

## 1. 要达到的体验

用户不用理解 Ollama、端口、环境变量、模型标签和语义索引。打开应用就能记录；想使用智能功能时，点击“一键准备 AI”，其余工作由应用完成。

完成标准：在一台没有 Ollama、Python、.NET SDK 的受支持 Windows x64 电脑上，使用普通用户权限，从应用界面完成准备并获得带来源的本地回答。准备完成后断网仍可使用。运行时和模型的下载需要网络，原始灵感仅交给本机推理。

## 2. 当前困惑的来源

- SettingsWindow 同时展示 AI 开关、服务地址、两个模型名称、命令行说明和索引操作；用户不知道先后顺序。
- start-local-ai.ps1 只解决开发工作区的服务启动，普通发布包没有附带其依赖的 .tools 目录。
- AppServices 连接既有服务，但不负责准备或管理它；填对设置也不代表服务已运行。
- 后台增量索引已存在，但缺少统一的准备进度、部分可用状态和恢复入口。

## 3. 推荐路线与取舍

**采用“应用托管的本机引擎 + 应用内下载准备”。** 默认使用独立目录、独立回环地址和应用自己管理的进程。避免修改系统 PATH、全局环境变量和用户另行安装的 Ollama。

保留两个边界：

- 已配置且可用的外部 Ollama：继续使用原有设置，不强制迁移；高级选项提供“使用已有服务”。只检查连接，不接管、停止、升级其进程。
- 完整离线 AI 包：后续可沿用相同清单和校验流程导入，本次不制作多个发行版本。

不采用“默认让用户安装独立 Ollama，再帮他填设置”：这仍留下外部软件启动、版本和路径的维护负担。也不在本次更换为 ONNX/llama.cpp 新推理实现：现有提供者已通过真实模型测试，先解决使用流程。

## 4. 用户可见流程

未准备时，设置中的“本地 AI”只有说明、空间估算和两个入口：

> 用自己的灵感进行智能搜索和问答。准备完成后可离线使用。
> 首次需要下载 AI 组件；预计下载量和所需磁盘空间将在检查后显示。
> **一键准备 AI**　　高级设置

应用打开该页面时自动做轻量检查，显示具体预计下载量、安装后占用和峰值所需空间，再允许用户开始下载。默认推荐目录空间足够时不额外询问。空间不足时直接提供“选择其他磁盘”。

准备中，按实际阶段显示状态：

1. 检查电脑和可复用组件。
2. 准备本地 AI 引擎。
3. 准备智能搜索组件。
4. 准备问答组件。
5. 检查功能并整理已有灵感。

显示当前阶段、文件下载进度、速度和已完成数量；未知时长不用虚假百分比或倒计时。准备页可关闭，任务仍随托盘应用在后台继续。提供“暂停 / 继续”；退出整个应用时停止任务，下次打开显示“继续准备”。准备完成提供“去试一试”。

准备后默认展示两个独立状态：“智能搜索：可用”“本地问答：可用”，以及必要时的“仍有 N 条灵感正在整理”。常用动作是“检查与修复”“关闭 AI”。模型名、端口、文件目录、手动索引修复都移入高级设置。

搜索/提问窗口在 AI 未准备时展示同一个准备入口，不把用户带到一组陌生配置项。关键词搜索始终可用。

## 5. 自动完成的工作

### 引擎与模型

- 先检查操作系统、架构、内存、安装目录可写性和磁盘余量；GPU 信息只用于加速建议，不要求用户提供 GPU 才能继续。
- 发布时使用固定、经过验证的运行时版本与模型清单，记录来源、大小和哈希/摘要；不在每次启动时追踪 latest 并静默升级。
- 第一版沿用已验证的 EmbeddingGemma 和 Qwen3 4B 组合，不让用户从模型市场做选择。可用内存不足或实际加载失败时保留智能搜索，明确显示问答尚不可用；较小问答模型需通过质量测试后再加入推荐清单。
- 引擎下载写入临时文件，支持服务器允许的 Range/ETag 恢复；不支持恢复时只重下未完成的文件。校验通过后解压到临时版本目录，防止路径穿越，验证入口后原子启用。
- 通过本机模型下载接口读取分层进度。取消请求后再次请求同一模型，复用已完成的层；恢复行为要在固定运行时上通过中断测试。
- 默认 AI 目录在资料目录下的 ai/，与数据库文件分开；备份/导出灵感不包含模型。允许空间不足时通过文件夹选择器指定另一磁盘。第一版不提供已安装模型的自动跨盘迁移。
- 当前开发工作区 .tools 中已下载的组件只作为已知位置的可选导入源，经校验后复用，不把硬编码 D:\NovelRAG 作为正式产品依赖。不扫描整个磁盘，不移动或删除原文件；复用时计入复制后的实际空间需求。

### 本机服务生命周期

- 使用隐藏子进程，配置仅对该进程生效的模型目录、本机地址和禁用云端选项。
- 从一小段候选端口中选择可用回环端口；处理检查后被占用的竞态，启动后核对本进程和健康状态，绝不把陌生服务当作自己启动成功。
- 启动与就绪检查设置超时；失败给出可操作的原因。
- 所有窗口共享一个准备任务和一个托管服务。多资料目录使用各自所有权记录，不能互相停止进程。
- 用户已启用 AI 时，后续启动自动恢复服务连接；模型按需加载，不要求打开应用就同时占满两套模型内存。
- 应用正常退出或异常终止时清理自己创建的进程树；Windows Job Object 用于管理托管进程及其推理子进程。不根据进程名或历史 PID 杀进程。

### 可用性与索引

- 先使用内置虚构素材做嵌入自检及简短、带来源的问答自检；文件下载完成不等于功能可用。
- 自检通过后自动保存相关配置并开放对应能力，不再要求额外点击“保存设置”。
- 搜索组件通过后可独立开放语义搜索；问答组件失败不回滚已可用的搜索能力。
- 原有索引机制继续按内容修订号和模型摘要处理缺失/过期条目。准备完成后自动接续，不要求手动重建。
- 有些记录尚未索引时说明检索范围不完整；只有引擎、两种模型自检通过且当前索引任务处理结束，才能显示整体准备完成。失败条目数量不得被“完成”状态掩盖。

## 6. 失败后的用户体验

- 网络中断：显示“下载中断，已完成部分会保留”，提供“继续准备”。自动重试有上限，避免无限等待。
- 下载源不可达：区分网络/证书/服务错误，提供重试和诊断详情。第一版不承诺绕过网络限制，也不自动转向未经验证的镜像。
- 磁盘不足：显示需要释放的空间，提供选择目录；仍可记录与普通搜索。
- 模型加载失败：尝试一次受控恢复；必要时使用 CPU 重试。持续失败显示“智能搜索可用，问答暂不可用”或相应实际状态。
- 端口冲突：托管模式自动换端口，不要求用户填写。
- 文件损坏：仅重新下载损坏组件；不能把删除整个 AI 目录或资料库当作修复方式。
- 用户关闭准备页：后台继续，不取消任务；退出应用则保存检查点，停止所属传输与进程。
- 再次点击准备：订阅同一个任务的进度，不启动第二份下载/索引。

## 7. 内部模块与改动范围

在现有分层上增加以下职责，不把下载/进程管理写进 SettingsWindow：

- Application：AiPreparationService、准备阶段/进度/能力状态记录；统一开始、暂停、继续、修复入口。
- Infrastructure：经过校验的组件清单、可恢复下载器、准备检查点、路径/磁盘检查、配置迁移。
- AI.Ollama：托管运行时管理、模型下载进度适配、能力自检；沿用现有 IEmbeddingProvider / ILLMProvider。
- Desktop：AiPreparationViewModel 和简化设置页面，绑定进度与操作；搜索窗口共用入口。
- Retrieval：复用 SemanticIndexer / IndexWorker；补齐与准备、退出、数据库恢复之间的取消和互斥。

用户“想启用 AI”的偏好、运行时是否健康、搜索是否可用、问答是否可用、索引是否完整分别记录。不能只用当前 AiEnabled 布尔值代表所有状态。检查点用原子写入；重启必须重新验证实际文件与服务，不能仅凭上次的“完成”标志放行。

现有手动配置和数据库均保留。配置迁移可回退；没有明确选用托管模式前，不覆盖已正常工作的外部服务设置。资料恢复会取消并等待索引任务，准备服务也必须尊重相同维护边界。

## 8. 实施顺序和验收

1. 准备状态机、配置兼容和模拟下载/进程接口；先测试重复点击、取消、重启恢复和部分可用。
2. 托管引擎准备、完整性校验、端口与进程所有权；测试损坏文件、磁盘不足、占用端口及外部服务隔离。
3. 模型下载、自检和自动索引；测试下载中断、模型失败、索引失败，以及失败时仍能保存和搜索原文。
4. 接入简化设置与搜索入口；真实窗口验证首次准备、关闭页面后继续、退出后恢复，以及后台状态提示。
5. 用没有 Ollama/Python/SDK 的干净 Windows 环境验收自包含发布包；断网验证已经准备好的能力；检查 8 GB/16 GB 内存设备上的失败提示与可用性，不凭内存数字承诺推理速度。

核心验收条件：正常机器上，用户不看 README、不打开终端、不填写任何技术字段，点击一次即可完成准备并提出一个有来源的中文问题。失败场景能够通过界面继续或修复，而不损伤已保存的灵感。

本次暂不包含应用自动更新、自动备份、模型市场、完整离线发行包和全套搜索界面改版。
